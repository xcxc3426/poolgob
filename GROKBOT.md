# Poolgob in Grok Bot

## One persistent operator

Create a named Poolgob Bot and give it [the operator instructions](GROKBOT-OPERATOR.md). Its job is to maintain a research file for the same watchlist, compare current evidence with earlier notes, and return a concise, attributed brief.

Grok Bot's documented workflow supports named Bots, persistent working context and file-based tasks. Poolgob supplies its own task wording, evidence contract and routines. Account setup and available product capabilities remain with the user and provider.

## The local boundary

The local engine computes the values in `case.json`. The operator reads those values and their assumptions. A prepared file is not a remote completion receipt. The pack's manifest is project metadata, not an official provider API configuration.

## A first task

> Use the attached Poolgob operator instructions and case.json. Read the source boundary and model assumptions first. Prepare research-note.md with the observed changes, measured exit conditions, concentration denominator, source IDs and unresolved gaps. Keep the note concise and distinguish recorded evidence from inference.

The task can be run in the user's Grok Bot conversation using the provided files. The [setup guide](GROKBOT-README.md) describes the handoff in detail.

## Stable context and current evidence

Stable watchlist preferences, note format and repeated unresolved questions can stay with the named operator. Current reserves, source timing and classifications must be read from the current packet. The role asks for missing inputs instead of silently using old values.

## Routine progression

Run one manual case, inspect the output, and ask the Bot to save the method as a reusable skill. Adapt the watchlist routine only after the file contract and sources are clear. Its owner, schedule, time zone, input location and missing-data behavior should all be explicit in the account's saved routine.
